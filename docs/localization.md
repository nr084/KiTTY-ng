# Локализация KiTTY-ng

## Общее ядро

`kittyng-i18n.h` и `utils/kittyng-i18n.c` предоставляют единый поиск UTF-8-переводов для Windows, Linux и macOS. В приложение встроены только English (`en`, старое значение 0) и Русский (`ru`, старое значение 1). Сохранённые настройки остаются совместимыми. Платформенные адаптеры отвечают за определение языка ОС, настройки и обновление интерфейса; ядро не читает файлы, не меняет настройки и не загружает DLL.

Источники — `locale/ru.json` и `locale/ru-contexts.json`. Английский исходный текст служит совместимым ключом для существующего кода PuTTY. Контекстные переопределения сохраняют необходимые различия интерфейсов. Генератор `python tools/generate-translations.py` создаёт таблицы, отсортированные по UTF-8; поиск двоичный, строки имеют время жизни процесса. Неизвестный ключ возвращается без изменения. Отсутствующий язык не подменяется русским.

Не переводятся пути, имена сеансов, SSH-данные, введённые команды и ответы удалённой стороны. Технические обозначения протоколов, алгоритмов и команд сохраняются. Переводить нужно шаблон сообщения до подстановки пользовательских значений.

## Изменение переводов

Обязательное правило разработки: **любая новая пользовательская строка клиента или утилит должна использовать общее языковое ядро либо его платформенный адаптер**. Это относится к Windows, Linux и macOS: меню, кнопкам, подсказкам, диалогам, ошибкам, подтверждениям, журналу и собственным сообщениям клиента в терминале. Английский ключ и русский перевод добавляются одновременно.

Новые локальные таблицы переводов, пары EN/RU в исходном коде и условные выражения выбора текста по языку не допускаются. Старые совместимые обёртки не являются образцом для нового кода. Для нового элемента сохраняется исходный ключ, а не только текущий отображаемый перевод. Протокольные идентификаторы, пути, команды, пользовательские данные и сообщения сервера под это правило перевода не подпадают.

1. Добавить английский шаблон и полный русский перевод в основной каталог.
2. Сохранить порядок и типы параметров форматирования, переносы строк и необходимые управляющие символы.
3. Добавить новую строку в соответствующие проверки покрытия/форматирования, перегенерировать таблицы и выполнить `tools/check-translations.py`, `tools/check-utility-translations.py` и тест `test_i18n`.
4. Проверить фактический интерфейс на обеих локалях, включая переключение языка, Unicode-пути и копирование журнала. Проверки macOS выполнять на Mac.

Новые UI-привязки должны хранить исходный ключ отдельно от отображаемого перевода. Обратный поиск существует для совместимости старых элементов; неоднозначный перевод не следует угадывать. Списки языков используют реестр ядра, а не позицию пункта как идентификатор.

## Будущее расширение

Другие языки предполагаются отдельными DLL, но в текущей реализации загрузчика нет. Перед его добавлением потребуется отдельный контракт версии ABI, владения строками, проверки форматных параметров и жизненного цикла модуля. Публичный интерфейс поиска отделён от хранения каталогов; добавление загрузчика не должно менять платформенные контролы. Механизм расширений Linux/macOS должен быть определён отдельно, без обещания загрузки Windows DLL на этих платформах.

## Текущий этап

Общий каталог и C-ядро внедряются вместе с исправлением сообщений журнала, подтверждения закрытия и первой максимизации окна вкладок Windows. Нативная проверка Mac и завершение миграции старых UI-привязок обязательны до объявления общей версии готовой.
