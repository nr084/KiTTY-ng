# Правила разработки kitty-ng

- Основная документация GitHub и заметки к релизам — на русском языке. Сохранять отдельный английский `README.en.md`, взаимные ссылки между README и благодарности авторам PuTTY и KiTTY в обеих версиях.
- В пользовательский changelog включать новые функции, исправления ошибок, изменения совместимости, безопасности и базовой версии PuTTY. Незначительные косметические изменения, например правки копирайта, не включать. Это не ограничивает обычную фиксацию изменений в Git.
- Использовать последнюю стабильную версию компилятора и сохранять точные сведения об инструментах сборки.
- Компилятор LLVM-MinGW устанавливать локально в `_tools/llvm-mingw/<выпуск>/toolchain` и сохранять между сборками. Перед обычной сборкой проверять последний стабильный выпуск; временные загрузки и промежуточные файлы удалять, установленный компилятор не считать временным файлом.
- Собирать и проверять выпуски локально через `python tools/local-build.py`; GitHub Actions для сборки не использовать.
- Версия выпуска имеет вид `<версия базового PuTTY>-<редакция KiTTY-ng>`, `0.85` — версия базового PuTTY, число после дефиса — номер нашего выпуска. `0.85-1` — первый обычный, не тестовый релиз KiTTY-ng; следующие выпуски на этой базе — `0.85-2`, `0.85-3` и т. д. Базовую часть не менять независимо от PuTTY. Редакция — положительное число; в ресурсах Windows хранить `0,85,1,0` для выпуска `0.85-1`. Обычные выпуски не помечать тестовыми.
- При публикации новых версий сохранять все предыдущие релизы GitHub и их вложения. Не удалять старые релизы, кроме случая нового прямого указания пользователя удалить конкретный релиз. Это правило заменяет прежнее указание удалять предыдущий релиз после публикации нового.
- При переходе на `0.85-1` по прямой команде пользователя удалить существующие релизы `test` из GitHub после успешной публикации. Это разовая очистка; последующие старые релизы сохранять.
- Вносить запрошенные изменения без автоматического выпуска релиза. Создавать и публиковать релиз, включая черновик GitHub, только после новой отдельной прямой команды пользователя на выпуск. Прежние указания публиковать релизы не считать разрешением на следующие выпуски. Без такой команды не повышать стадию версии и не создавать релизные теги; локальная сборка и проверка изменений допускаются.
- По новой прямой команде «делай релиз» увеличивать редакцию KiTTY-ng после дефиса на один относительно последнего опубликованного выпуска: после `0.85-1` выпускать `0.85-2`, далее `0.85-3` и т. д. Затем синхронизировать версию в файлах и ресурсах EXE, локально собрать и проверить три архитектуры и опубликовать релиз GitHub с архивами. При повторе незавершённого выпуска использовать уже выбранный номер, не увеличивать его повторно. До новой команды сохранять текущую подготовленную версию (сейчас `0.85-6`), не повышать номер заранее и не публиковать следующий релиз.
- Выпуск содержит macOS Universal DMG, Linux x86_64 AppImage/AppDir и три Windows ZIP: x64, x86 и ARM64. В имени ZIP указывать версию и архитектуру. Внутри использовать обычные имена EXE без номера версии; все утилиты должны соответствовать архитектуре архива. Встроенные версии EXE сохранять.
- Основной клиент называть `kitty-ng-x86.exe`, `kitty-ng-x64.exe` и `kitty-ng-arm64.exe` соответственно архитектуре; номер версии в имя EXE не добавлять.
- Утилиты внутри ZIP называть `klink-<архитектура>.exe`, `kscp-<архитектура>.exe`, `ksftp-<архитектура>.exe`, `kittygen-<архитектура>.exe`, `kageant-<архитектура>.exe`, где архитектура — `x86`, `x64` или `arm64`.
- При автоматическом запуске клиента и сопутствующих утилит использовать EXE своей архитектуры из каталога вызывающего приложения; проверять архитектуру PE, не подменять отсутствующий файл программой другой архитектуры или найденной через PATH.
- Сохранять совместимость с портативным форматом KiTTY и ранее созданными настройками. Идентификаторы формата хранения не менять ради косметического переименования.
- Ветка реестра проекта — `HKCU\Software\KiTTY-NG`, маркер портативного режима — `kitty-ng.portable`, переменная каталога — `KITTY_NG_PORTABLE_DIR`. Использовать только актуальное имя проекта; это явное правило именования не меняет формат файлов оригинального KiTTY.
- Не добавлять чтение, импорт или автоматическую миграцию настроек прежнего названия проекта: его ветки реестра, портативного маркера и переменной окружения не поддерживать. Совместимость с портативным форматом оригинального KiTTY сохранять.
- После каждой работы самостоятельно удалять временные загрузки, временные зависимости, промежуточные каталоги и ненужные локальные пакеты/папки старых релизов, без отдельного напоминания. Текущие готовые пакеты сохранять в `dist`, результаты успешно пройденных проверок и установленные компиляторы/SDK сохранять. Эта локальная очистка не затрагивает релизы и вложения GitHub.
- Не повторять уже успешно пройденные тесты, если проверяемая ими логика не изменилась. Запускать проверки изменённой логики, новых тестов и воспроизведения новых ошибок; результаты успешных незатронутых проверок сохранять и использовать повторно.

- При отсутствии сохранённого выбора использовать язык интерфейса Windows: русский для LANG_RUSSIAN, английский для остальных. Сохранённый выбор и явный `--language en|ru` имеют приоритет. KiTTYgen переключает язык отдельным меню «Язык» с сохранением настройки и открытого ключа.

- В портативных сеансах сохранять SSH-ключи (`PublicKeyFile`) и отдельные SSH-сертификаты (`DetachedCertificate`) внутри выбранного портативного корня относительными путями. Разрешать сохранённые относительные пути от портативного корня, независимо от CWD и каталога файла сеанса; внешние ключи сохранять абсолютными путями. Использовать общий механизм чтения/записи для клиента и консольных утилит. Не менять семантику произвольных CLI-путей, файлов журналов, операций KiTTYgen/Kageant и реестровых настроек.
- Тот же принцип относительных ссылок применять к `Scriptfile` и `IconeFile`. Массовое обновление преобразует также явно распознанные файловые ссылки `Autocommand`; обычные удалённые команды сохранять без изменений.
- Объём миграции KiTTY зафиксирован в `docs/migration.md` и `docs/kitty-migration-decisions.json`. При изменении решений обновлять матрицу и проверять `python tools/audit-kitty.py`; сохранение неизвестных полей не считать поддержкой исключённой функции.

## Отложенные задачи

- Пока не реализовывать: добавить в KiTTYgen и остальные сопутствующие утилиты (Kageant, Klink, Kscp, Ksftp) копирайт KiTTY-ng по образцу основного клиента: знак ©, `nr084`, год компиляции. Существующие уведомления PuTTY и KiTTY сохранить и разделить, как в клиенте. Выполнять только после отдельной команды пользователя на реализацию. Эту косметическую правку не включать в пользовательский changelog и заметки к релизу.

## Постоянное разделение сборок между Windows и Mac

- В чате на Windows собирать только Windows и Linux. Не запускать сборку macOS на Windows, в том числе кросс-сборку, даже при общей команде выпустить все платформы.
- macOS собирать и проверять только локально в отдельном чате на настоящем Mac, в той же синхронизируемой папке проекта KiTTY-NG. Исходники macOS разрешается исправлять из Windows-чата; это не является подтверждением сборки или проверки на Mac.
- После готовности Windows/Linux готовить отдельный самодостаточный промпт для Mac-чата: папка проекта, согласованная версия и ревизия исходников, необходимые изменения, команды нативной сборки Universal 2/DMG, проверки, обновление скриншотов и порядок передачи артефактов для публикации.
- Для общего выпуска использовать один номер версии на всех платформах. Не повышать его повторно в Mac-чате; не объявлять синхронный выпуск полностью готовым до получения проверенного Mac-пакета той же версии. Сохранять уже подготовленные Windows/Linux-пакеты и прежние релизы.
- Указания ниже о сборке, съёмке скриншотов и публикации «из текущего Mac-чата» относятся только к чату, фактически работающему на Mac, и не разрешают выполнять Mac-сборку на Windows.

## macOS

- Разрабатывать macOS как отдельный нативный AppKit-порт; текущие ограничения отражать в `docs/macos.md`, не выдавать Windows-миграцию за завершённый Mac-порт.
- Приложение и каждый помощник должны быть Universal 2: arm64 + x86_64. Собирать и проверять локально на Mac через `python3 tools/local-build.py --platform macos`; на Windows macOS-приложение больше не собирать.
- Корень портативных данных — каталог рядом с `.app` и Windows EXE, данные не писать внутрь подписанного bundle. Сохранять общий формат KiTTY; специфичные Mac-настройки отделять от Windows-полей.
- SDK и компиляторы сохранять в `_tools/macos`; проверять стабильные версии и записывать происхождение. SDK не добавлять в Git или архив приложения.
- Локальные Mac-preview не являются релизами. Сборку и проверку подписи отличать от запуска на Mac; не заявлять runtime-проверку без её результата.

## Публикация из текущего Mac-чата

- Прямая команда пользователя «делай релиз» здесь означает локальную сборку, проверки, обновление документации и публикацию в прежний GitHub-репозиторий `nr084/kitty-ng`, как в Windows-процедуре. Не останавливаться на готовых локальных архивах.
- Если пользователь прямо просит обновить Mac-часть уже опубликованного выпуска, сохранять его номер, тег и Windows/Linux-вложения. Старый Mac-пакет сохранять отдельным архивным вложением; стандартное имя использовать для нового проверенного DMG. Прежние релизы не удалять.
- Нужные скриншоты macOS снимать самостоятельно на этом Mac с синтетическими профилями/ключами и обновлять русскую и английскую документацию.
