# Правила разработки kitty-ng

- Основная документация GitHub и заметки к релизам — на русском языке. Сохранять отдельный английский `README.en.md`, взаимные ссылки между README и благодарности авторам PuTTY и KiTTY в обеих версиях.
- В пользовательский changelog включать новые функции, исправления ошибок, изменения совместимости, безопасности и базовой версии PuTTY. Незначительные косметические изменения, например правки копирайта, не включать. Это не ограничивает обычную фиксацию изменений в Git.
- Всегда использовать последний стабильный (stable) выпуск компилятора для соответствующей платформы. Перед каждой сборкой, включая повторную сборку текущей версии, проверять актуальный stable у официального поставщика; если установленный компилятор устарел, сначала обновить его. Не использовать beta/RC/nightly вместо stable. Сохранять точную версию и происхождение инструментов в отчёте сборки.
- Компилятор LLVM-MinGW устанавливать локально в `_tools/llvm-mingw/<выпуск>/toolchain` и сохранять между сборками. Перед обычной сборкой проверять последний стабильный выпуск; временные загрузки и промежуточные файлы удалять, установленный компилятор не считать временным файлом.
- Собирать и проверять выпуски локально через `python tools/local-build.py`; GitHub Actions для сборки не использовать.
- Версия выпуска имеет вид `<версия базового PuTTY>-<редакция KiTTY-ng>`, `0.85` — версия базового PuTTY, число после дефиса — номер нашего выпуска. `0.85-1` — первый обычный, не тестовый релиз KiTTY-ng; следующие выпуски на этой базе — `0.85-2`, `0.85-3` и т. д. Базовую часть не менять независимо от PuTTY. Редакция — положительное число; в ресурсах Windows хранить `0,85,1,0` для выпуска `0.85-1`. Обычные выпуски не помечать тестовыми.
- По постоянному указанию пользователя от 28 октября 2026 в GitHub Releases хранить только последний опубликованный стабильный выпуск KiTTY-ng и последний опубликованный стабильный выпуск независимого плагина kitty-ng-fs. После успешной публикации и проверки нового выпуска удалять предыдущие релизы соответствующего продукта вместе с вложениями; последний релиз другого продукта и его вложения сохранять. До успешной проверки нового выпуска старый не удалять. Историю релизных пакетов и архивные вложения в GitHub не хранить. Это правило заменяет прежние указания сохранять все релизы. Git-коммиты и теги этим правилом не удаляются.
- При переходе на `0.85-1` по прямой команде пользователя удалить существующие релизы `test` из GitHub после успешной публикации. Это разовая очистка; последующие старые релизы сохранять.
- Вносить запрошенные изменения без автоматического выпуска релиза. Создавать и публиковать релиз, включая черновик GitHub, только после новой отдельной прямой команды пользователя на выпуск. Прежние указания публиковать релизы не считать разрешением на следующие выпуски. Без такой команды не повышать стадию версии и не создавать релизные теги; локальная сборка и проверка изменений допускаются.
- По новой прямой команде «делай релиз» увеличивать редакцию KiTTY-ng после дефиса на один относительно последнего опубликованного выпуска: после `0.85-1` выпускать `0.85-2`, далее `0.85-3` и т. д. Затем синхронизировать версию в файлах и ресурсах EXE, локально собрать и проверить три архитектуры и опубликовать релиз GitHub с архивами. При повторе незавершённого выпуска использовать уже выбранный номер, не увеличивать его повторно. До новой команды сохранять текущую подготовленную версию (сейчас `0.85-10`), не повышать номер заранее и не публиковать следующий релиз.
- Выпуск содержит macOS Universal DMG, Linux x86_64 AppImage/AppDir и три Windows ZIP: x64, x86 и ARM64. В имени ZIP указывать версию и архитектуру. Внутри использовать обычные имена EXE без номера версии; все утилиты должны соответствовать архитектуре архива. Встроенные версии EXE сохранять.
- Основной клиент называть `kitty-ng-x86.exe`, `kitty-ng-x64.exe` и `kitty-ng-arm64.exe` соответственно архитектуре; номер версии в имя EXE не добавлять.
- Утилиты внутри ZIP называть `klink-<архитектура>.exe`, `kscp-<архитектура>.exe`, `ksftp-<архитектура>.exe`, `kittygen-<архитектура>.exe`, `kageant-<архитектура>.exe`, где архитектура — `x86`, `x64` или `arm64`.
- При автоматическом запуске клиента и сопутствующих утилит использовать EXE своей архитектуры из каталога вызывающего приложения; проверять архитектуру PE, не подменять отсутствующий файл программой другой архитектуры или найденной через PATH.
- Сохранять совместимость с портативным форматом KiTTY и ранее созданными настройками. Идентификаторы формата хранения не менять ради косметического переименования.
- Ветка реестра проекта — `HKCU\Software\KiTTY-NG`, маркер портативного режима — `kitty-ng.portable`, переменная каталога — `KITTY_NG_PORTABLE_DIR`. Использовать только актуальное имя проекта; это явное правило именования не меняет формат файлов оригинального KiTTY.
- Не добавлять чтение, импорт или автоматическую миграцию настроек прежнего названия проекта: его ветки реестра, портативного маркера и переменной окружения не поддерживать. Совместимость с портативным форматом оригинального KiTTY сохранять.
- После каждой работы самостоятельно удалять временные загрузки, временные зависимости, промежуточные каталоги и ненужные локальные пакеты/папки старых релизов, без отдельного напоминания. Текущие готовые пакеты сохранять в `dist`, результаты успешно пройденных проверок и установленные компиляторы/SDK сохранять. Эта локальная очистка не затрагивает релизы и вложения GitHub.
- Не повторять уже успешно пройденные тесты, если после их выполнения не было изменений, относящихся к этим проверкам. Это постоянное правило для всех платформ, повторных сборок и продолжения работы в другом чате. Перед запуском определить затронутые проверки по изменениям проверяемого кода, его зависимостей, самих тестов, настроек сборки, компилятора и среды выполнения. Запускать только затронутые проверки, новые тесты и проверки воспроизведения новых ошибок. Изменения документации, скриншотов или несвязанной платформы сами по себе не являются основанием повторять успешные тесты.
- Сохранять отчёты успешных проверок и штатно использовать их повторно с указанием исходного коммита, проверенных бинарников и условий выполнения. Не выдавать повторно использованный результат за новый запуск и не переписывать его происхождение. При отсутствии достоверного отчёта или невозможности установить применимость результата выполнить соответствующую проверку заново; это не основание перезапускать все остальные тесты.

- При отсутствии сохранённого выбора использовать язык интерфейса Windows: русский для LANG_RUSSIAN, английский для остальных. Сохранённый выбор и явный `--language en|ru` имеют приоритет. KiTTYgen переключает язык отдельным меню «Язык» с сохранением настройки и открытого ключа.

- В портативных сеансах сохранять SSH-ключи (`PublicKeyFile`) и отдельные SSH-сертификаты (`DetachedCertificate`) внутри выбранного портативного корня относительными путями. Разрешать сохранённые относительные пути от портативного корня, независимо от CWD и каталога файла сеанса; внешние ключи сохранять абсолютными путями. Использовать общий механизм чтения/записи для клиента и консольных утилит. Не менять семантику произвольных CLI-путей, файлов журналов, операций KiTTYgen/Kageant и реестровых настроек.
- Тот же принцип относительных ссылок применять к `Scriptfile` и `IconeFile`. Массовое обновление преобразует также явно распознанные файловые ссылки `Autocommand`; обычные удалённые команды сохранять без изменений.
- Объём миграции KiTTY зафиксирован в `docs/migration.md` и `docs/kitty-migration-decisions.json`. При изменении решений обновлять матрицу и проверять `python tools/audit-kitty.py`; сохранение неизвестных полей не считать поддержкой исключённой функции.

## Отложенные задачи

- По прямой команде пользователя от 28 октября 2026 реализовать для Windows/Linux в обновлении 0.85-10 без повышения версии: добавить в KiTTYgen и остальные сопутствующие утилиты (Kageant, Klink, Kscp, Ksftp) копирайт KiTTY-ng по образцу основного клиента: знак ©, `nr084`, год компиляции, дату сборки и домашнюю страницу проекта `https://github.com/nr084/kitty-ng`. Для GUI разместить сведения в «О программе», для консольных утилит — в выводе версии/информации о программе. Дату и год получать из данных сборки, не задавать вручную; подписи выводить через языковое ядро. Существующие уведомления PuTTY и KiTTY сохранить и разделить, как в клиенте. Mac-адаптацию выполнять нативно отдельным чатом. Эту косметическую правку не включать в пользовательский changelog и заметки к релизу.

## Постоянное разделение сборок между Windows и Mac

- Постоянный порядок по уточнению пользователя от 28 октября 2026: Windows-чат завершает правки, сборку и проверки Windows/Linux и выдаёт пользователю самодостаточный промпт для Mac с точным коммитом. Mac-чат учитывает и адаптирует все изменения общего выпуска (включая интерфейс вкладок и кнопки закрытия), собирает и нативно проверяет macOS, но ничего не публикует. Пользователь сообщает Windows-чату о готовности Mac; только после этого Windows-чат проверяет общий комплект и публикует все платформы. Не публиковать общий выпуск до этого сообщения. Если Mac исправляет исходники, заново согласовать коммит и при необходимости штатно пересобрать Windows/Linux, повторно используя незатронутые успешные проверки.

- Общий выпуск ведёт Windows-чат: согласует версию и исходный коммит, собирает Windows/Linux, принимает проверенный Mac-пакет, собирает общий манифест и публикует все платформы на GitHub. Mac-чат собирает и проверяет только macOS, обновляет Mac-документацию/скриншоты и сообщает пользователю о готовности с коммитом, путём к DMG, SHA-256 и отчётами. Самостоятельно общий выпуск из Mac-чата не публиковать.

- В чате на Windows собирать только Windows и Linux. Не запускать сборку macOS на Windows, в том числе кросс-сборку, даже при общей команде выпустить все платформы.
- macOS собирать и проверять только локально в отдельном чате на настоящем Mac, в той же синхронизируемой папке проекта KiTTY-NG. Исходники macOS разрешается исправлять из Windows-чата; это не является подтверждением сборки или проверки на Mac.
- После готовности Windows/Linux готовить отдельный самодостаточный промпт для Mac-чата: папка проекта, согласованная версия и ревизия исходников, необходимые изменения, команды нативной сборки Universal 2/DMG, проверки, обновление скриншотов и порядок передачи артефактов для публикации.
- Для общего выпуска использовать один номер версии на всех платформах. Не повышать его повторно в Mac-чате; не объявлять синхронный выпуск полностью готовым до получения проверенного Mac-пакета той же версии. Сохранять уже подготовленные Windows/Linux-пакеты до завершения общего выпуска; старые GitHub-релизы удалять после проверки нового по правилу хранения выше.
- Mac-задачи по сборке, проверке и съёмке скриншотов выполнять только на настоящем Mac; готовые артефакты и отчёты передавать Windows-чату для общей публикации.

## macOS

- Разрабатывать macOS как отдельный нативный AppKit-порт; текущие ограничения отражать в `docs/macos.md`, не выдавать Windows-миграцию за завершённый Mac-порт.
- Приложение и каждый помощник должны быть Universal 2: arm64 + x86_64. Собирать и проверять локально на Mac через `python3 tools/local-build.py --platform macos`; на Windows macOS-приложение больше не собирать.
- Корень портативных данных — каталог рядом с `.app` и Windows EXE, данные не писать внутрь подписанного bundle. Сохранять общий формат KiTTY; специфичные Mac-настройки отделять от Windows-полей.
- SDK и компиляторы сохранять в `_tools/macos`; проверять стабильные версии и записывать происхождение. SDK не добавлять в Git или архив приложения.
- Локальные Mac-preview не являются релизами. Сборку и проверку подписи отличать от запуска на Mac; не заявлять runtime-проверку без её результата.

## Передача готовой macOS-сборки Windows-чату

- Прямая команда пользователя «делай релиз» в Mac-чате означает подготовить согласованную Mac-часть: локально собрать Universal 2/DMG, выполнить нативные проверки, обновить документацию и сообщить о готовности. Ведущий Windows-чат публикует общий выпуск в `nr084/kitty-ng`. Это правило заменяет прежнее указание публиковать общий выпуск из Mac-чата.
- При обновлении Mac-части уже опубликованного выпуска подготовить проверенный DMG и передать Windows-чату для публикации. Сохранять номер, тег и Windows/Linux-вложения. Стандартное имя использовать для нового проверенного DMG; старый Mac-пакет и архивные вложения после проверки замены удалять. Сохранять только последние выпуски клиента и плагина по правилу выше.
- Нужные скриншоты macOS снимать самостоятельно на этом Mac с синтетическими профилями/ключами и обновлять русскую и английскую документацию.

## Независимое происхождение платформ (уточнение 28 октября 2026)

- Для общего выпуска требуется одинаковая версия Windows, Linux и macOS, но не одинаковый Git-коммит. Каждая платформа собирается из своего чистого коммита; её отчёты, проверки и хеши должны соответствовать именно поставляемым бинарникам. В общем манифесте сохранять отдельный коммит каждой платформы, не переписывать происхождение существующих пакетов.
- Не пересобирать незатронутую платформу только ради совпадения коммита. В частности, проверенный Mac-пакет той же версии можно сохранить при исправлениях Windows/Linux. Это правило заменяет прежние требования общего коммита и обязательной Mac-переупаковки после любых изменений Windows/Linux.
- Разовое разрешение пользователя: выполнить запланированные исправления локализации/кодировки и первого дублирования окна и обновить опубликованный 0.85-8 без повышения версии. Это не разрешает будущие обновления опубликованных выпусков без отдельной команды. При замене вложений сначала загрузить и проверить замену, затем убрать старое вложение; незатронутые пакеты и релиз плагина сохранять. Исторический релизный тег не переносить, новые коммиты пакетов указывать в манифесте и заметках.

## Языковое ядро (28 октября 2026)

- Обязательное правило для новых строк: весь добавляемый пользовательский текст клиента и утилит на Windows, Linux и macOS (меню, кнопки, подсказки, диалоги, ошибки, подтверждения, журнал и собственные сообщения входа в терминале) выводить через общее языковое ядро или его платформенный адаптер. Одновременно добавлять английский ключ и полный русский перевод в общий каталог. Не создавать новые отдельные таблицы переводов, пары EN/RU в коде или ветвления по языку ради выбора текста. Существующие такие конструкции не использовать как образец для новых сообщений.
- Переводить шаблон до подстановки значений; пользовательские и серверные данные сохранять буквально. Для новых строк расширять соответствующие проверки покрытия и форматных параметров, перегенерировать таблицы и проверять русский/английский интерфейс. Подробности — `docs/localization.md`.

- Встроенные языки клиента и утилит — только русский и английский. Общее ядро на C и UTF-8-каталоги используются всеми платформами. Другие языки в будущем предполагаются отдельными DLL; загрузчик DLL и дополнительные языки сейчас не реализовывать.
- Основной редактируемый каталог — `locale/ru.json`, контекстные формулировки — `locale/ru-contexts.json`. Генерируемые таблицы вручную не редактировать. Добавляемые сообщения проверять на полноту перевода и совместимость параметров форматирования. Не переводить содержимое терминала, данные пользователя или сообщения удалённого сервера.
- После согласования общего языкового рефакторинга подготовка следующего общего выпуска заменяет план тихого обновления 0.85-8. Опубликованный 0.85-8 пока не заменять. Mac адаптируется и проверяется нативно; Windows-чат не объявляет непроверенную Mac-часть готовой.

## Поэтапная публикация Windows/Linux и macOS (последнее уточнение 28 октября 2026)

- По новому указанию пользователя Windows-чат публикует проверенные Windows/Linux-пакеты нового выпуска, затем передаёт самодостаточный промпт Mac-чату. Mac-чат поднимает macOS до того же номера версии, адаптирует изменения, нативно собирает и проверяет Universal 2/DMG, готовит скриншоты и самостоятельно публикует Mac-вложение в этот же выпуск. Ожидать обратного подтверждения для публикации Mac через Windows-чат больше не требуется.
- Mac-чат не заменяет Windows/Linux-вложения, не переносит релизный тег и не повышает номер второй раз. Проверяет SHA-256 загруженного DMG, обновляет описание готовности macOS и документацию. Отчёты сохраняют реальные отдельные коммиты платформ.
- До добавления Mac-пакета описание релиза прямо указывает, что macOS готовится; такой выпуск не выдавать за проверенный комплект всех шести пакетов. Это правило заменяет прежний запрет публикации до получения Mac и прежнее требование публикации всех платформ исключительно Windows-чатом.
